The Dayfolio archive format

Format version 1, as Dayfolio 1.0 writes it on the Mac, iPhone and iPad. This page is for anyone who wants to read their journals without Dayfolio, or move them somewhere else: it describes the .dayfolio file completely enough to write a reader for it. It was written from the code (Packages/DayfolioKit/Sources/DayfolioStore/Archive/ and Sync/SyncSchema.swift), and a test (ArchiveFormatDocTests) checks it against the code: every record type, key, listed value and synced setting the app writes has a row here.

A Dayfolio archive holds everything needed to bring journals back on any device: journals, templates, entries with their snapshots, the files added to them, people, projects, places, reminders, saved searches, report presets and Reports, what is in Recently deleted, and the settings that sync. Export… with Dayfolio archive writes one; Import… restores one. Restoring adds only what is missing and never changes or removes anything already there (ADR 0004).

An archive isn't encrypted. Anyone who has the file can read everything in it, journals you lock included (Dayfolio asks for Face ID or Touch ID before it writes one that holds them).

1. The container

  • A ZIP archive (PKZIP 2.0, with Zip64 where a file or the archive needs it). Renamed to .zip, any unzip tool opens it.
  • File name extension .dayfolio; uniform type net.ninjaapps.apps.dayfolio.archive, which conforms to public.zip-archive. Dayfolio suggests Dayfolio.dayfolio for everything and the journal's name for one journal (Engineering Log.dayfolio).
  • Written owner-only (0600) where the disk keeps permissions.

  • manifest.json comes first, then the records files in alphabetical order, then the files.
  • records/<RecordType>.json holds every record of one type (section 4). Every type is there, an empty one as "records": [].
  • files/<attachment id> holds the original bytes of one attachment, exactly as they were added, named by the attachment's id (an uppercase UUID).
  • The JSON files are deflated. The files are stored uncompressed, and written and read a piece at a time, so an archive can be far larger than memory.
  • Every entry in the ZIP has the archive's creation time as its modification time.
  • A path is /-separated. A record type is ASCII letters, digits and _ only, so a records file can't name a path outside records/.

When it reads an archive, Dayfolio ignores entries it doesn't recognise, never follows a symbolic link, and refuses an archive with more than 100,000 entries, a records file over 256 MB, or records over 512 MB in all, decompressed. A file over 50 MB, the cap on every attachment, isn't restored.

2. Versions, and what a reader should tolerate

  • formatVersion in the manifest says which format the archive is. This page describes 1, the only one so far. Dayfolio refuses a higher version ("This archive was made by a newer version of Dayfolio.") and treats an archive with no readable manifest, or a version below 1, as not an archive.
  • Format 1 only grows by addition. A later Dayfolio may add optional manifest keys (as nameOnlyReferences was added), keys on a record, record types, field types and values of a listed key, all without changing the version. A reader should skip what it doesn't know rather than fail. Dayfolio itself does: it keeps a key it doesn't know with its record, and sends it on with it; it keeps a record of a type it doesn't know aside until an update can read it; and it keeps a field, or a field value, of a type it doesn't know in its place.
  • appVersion names the version of Dayfolio that wrote the archive. It's for people, not for parsing.

4. records/<RecordType>.json

{"recordType":"Place","records":[{"id":"6E977FB0-ECF9-4A80-882A-D0D6BC910976","values":{"city":{"s":"Warsaw"},"createdAt":{"t":793785600},"latitude":{"d":52.223},"longitude":{"d":21.019},"name":{"s":"Home"},"radius":{"d":150},"street":{"s":"Mokotowska"},"updatedAt":{"t":793785600}}}]}
  • recordType is the file's record type, the name iCloud uses for it too.
  • Each record's id is an uppercase UUID: the same id the record has in Dayfolio and in iCloud. Records point at each other by these ids.
  • values holds the record's keys, each with one typed value. A key that isn't there has no value.
  • The JSON is written with its keys sorted, and / isn't escaped.

Every value is an object with one key that says its type:

FormHolds
{"s": "…"}A string: text, an id, one of a listed set of words, or JSON written into a string (below).
{"i": 4}A 64-bit integer. A yes-or-no key is 0 or 1.
{"d": 52.223}A floating-point number.
{"t": 811951200}A date: seconds since 1 January 2001, 00:00:00 UTC (Apple's reference date), to the millisecond. Add 978,307,200 for Unix time.
{"b": "…"}Bytes, in base64.

JSON in a string. Some keys hold JSON written into a string, in canonical form (keys sorted, no white space): the ones whose type below is JSON. Inside them, a date is an ISO 8601 string in UTC with milliseconds ("2026-09-24T09:12:00.000Z"), an id is an uppercase UUID string, and section 6 gives each shape.

5. Record types

They are listed parents first, the order a restore adds them in. Three keys mean the same thing wherever they appear: createdAt (made), updatedAt (last changed: sync merges by it) and deletedAt (put in Recently deleted; Dayfolio removes it for good 30 days after that, counted by each device). A record in Recently deleted is in the archive with its deletedAt, so a restore brings it back to Recently deleted, not to the journal.

6.8 Colours

  • A journal colour, used by journals, templates, people and projects: orange, blue, green, purple, teal, pink, amber or slate.

7. What restoring does

Dayfolio restores an archive inside one database transaction, record by record in the order of section 5: all of it is added or none of it is. Cancelling, or iOS running out of time, adds nothing. Before you confirm, it shows the archive's journal names and the dates of its entries (never their content, and a journal marked locked doesn't widen the dates), and how much it would add.

  • A record already on the device wins, untouched, whether it's live, archived or in Recently deleted. Ids decide: a record is "already here" when a record of that type has its id.
  • A missing record is added with its own id and values, dates included, so something deleted for good since comes back as it was.
  • Recently deleted: a record whose deletedAt is more than 30 days ago comes back with a fresh 30 days from the restore.
  • Journal: a defaultTemplateID that is on neither side is dropped.
  • JournalTemplate, DismissedReminderSuggestion: skipped without both their Journal and their Template. A journal holds a template once, and a suggestion is dismissed once. A membership of a journal that was already on the device goes after the templates it has.
  • Person, Project: one with the same nameKey as one on the device isn't added; the entries that name it name the one on the device, which keeps its own rate, or none. Among the archive's own, the earliest made is kept. One in nameOnlyReferences comes back hidden, for its name only, and never goes up to iCloud as a live record.
  • Entry: skipped without its Journal. A Template neither side has comes back hidden, made from the entry's snapshot. An entry of a journal in Recently deleted joins it there.
  • Attachment: skipped without its Entry. Its file name is made safe for a disk, and its extension follows its contentType. Its bytes come from files/<id> unless the device has them already, and are checked against the ZIP's checksum; a file missing from the archive, damaged or over 50 MB is skipped, and its entry is still restored. A restored file is marked as downloaded, like any file from the internet.
  • Reminder: skipped without its Journal; a templateID on neither side is dropped.
  • Report: skipped without its ReportPreset. A Report of a preset in Recently deleted joins it there. When the device already has a live Report of the same preset for the same range, the archived one goes to Recently deleted.
  • SyncedSetting: only on a device with no journals at all, and a setting changed there later than the archive's stays.
  • Keys and records a newer Dayfolio wrote are kept with their record, or kept aside, as in section 2.
  • Afterwards tags, search, mentions and references are rebuilt for what was added, and text in its files is read again in the background.
  • Whatever couldn't come back is listed on the result, each item by what it was ("Nothing was skipped." otherwise). Everything added goes up to iCloud like any other change.

8. Reading an archive yourself

The archive's content is plain JSON and the original files. This Python 3 program (no packages to install) prints every live entry with its journal, template and title, and the text of its text fields:

import datetime, json, sys, zipfile

REFERENCE = datetime.datetime(2001, 1, 1, tzinfo=datetime.timezone.utc)

def plain(typed):
    """A record's typed value as Python: str, int, float, datetime or bytes."""
    (kind, value), = typed.items()
    if kind == "t":
        return REFERENCE + datetime.timedelta(seconds=value)
    return value  # "s", "i", "d"; "b" stays base64

with zipfile.ZipFile(sys.argv[1]) as archive:
    manifest = json.loads(archive.read("manifest.json"))
    if manifest["formatVersion"] > 1:
        sys.exit("made by a newer Dayfolio")

    def records(kind):
        try:
            data = json.loads(archive.read(f"records/{kind}.json"))
        except KeyError:
            return {}
        return {r["id"]: {k: plain(v) for k, v in r["values"].items()} for r in data["records"]}

    journals = records("Journal")
    for entry in sorted(records("Entry").values(), key=lambda e: e["date"]):
        if "deletedAt" in entry:
            continue  # in Recently deleted
        snapshot = json.loads(entry["snapshot"])
        values = json.loads(entry.get("fieldValues", "{}"))
        journal = journals.get(entry["journalID"], {}).get("name", "?")
        when = entry["date"].astimezone()  # dates are UTC; this is the computer's own time zone
        print(f'{when:%Y-%m-%d %H:%M} · {journal} · {snapshot["templateName"]} · {entry.get("title", "")}')
        for field in snapshot["fields"]:
            value = values.get(field["id"], {})
            if value.get("type") in ("text", "richText"):
                print(f'  {field["label"]}: {value["value"]}')

python3 read-dayfolio.py "Engineering Log.dayfolio" prints one line per entry, oldest first, each followed by its text fields.
